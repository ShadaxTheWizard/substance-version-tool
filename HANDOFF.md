# Handoff: Substance Version Tool

Makes a Substance 3D Painter project (`.spp`) open in an older Painter release, any of
9.0 – 12.2, by rewriting it in that release's exact file format. Substance 3D Designer
support is planned (nothing written for it yet). Public at
https://github.com/ShadaxTheWizard/substance-version-tool, MIT-licensed, maintained by
Shadax. Not affiliated with Adobe.

## Releasing

Bump `__version__` in `spp_convert.py`, commit, then
`git tag -a vX.Y.Z -m "…" && git push origin main vX.Y.Z`. The tag must equal
`__version__` (both build scripts check). The `release` job creates the GitHub release with
every file and its `.sha256`, notes from `packaging/release-notes.md` (`{version}` is
substituted; the `<!-- unsigned -->` block is dropped once signing is configured).
Installed apps that opted in see the new version on their next start.

Pushing: this machine's SSH key is not on GitHub; push over HTTPS with
`git -c credential.helper= -c 'credential.helper=!gh auth git-credential' push`, or run
`gh auth setup-git` once. The `gh` login needs the `workflow` scope to push changes under
`.github/workflows/`.

## The app

`substance_version_tool.py` is a PySide6 window around `spp_convert.convert()`: a project list
(drag and drop, shows the saving release), a target selector, output next to the project or
in a folder, the texture-cache option, the report, and a Help menu (updates, About).
Conversion runs in a `QThread`; the CLI is unchanged. `--open FILE.spp` (what the `.desktop`
entry runs, with `MimeType` for `.spp`) skips the window: `Opener` finds the newest installed
Painter, converts with `spp_convert.copy_for()` when the project is newer than it (same copy
name and reuse rule as the launcher's `--launch`), and starts Painter with the result. It
falls back to the window when no Painter is found or the conversion fails. Tested on Linux
from a checkout against a stub Painter with 12.2 and 12.1 projects. `--self-test` (with
`QT_QPA_PLATFORM=offscreen`) is what CI runs on each build; it reports on stdout and in
`$SPP_SELFTEST_LOG`, and turns failures into exit code 1 (the Windows build has no console,
and an uncaught exception there opens a dialog). `--check-update` prints the newest release
and how this copy would update. Decisions: PySide6 (`PySide6-Essentials` only), PyInstaller
`--onedir`, an AppImage for Linux, an Inno Setup installer plus a portable zip for Windows,
GitHub releases.

The icon (`packaging/substance-version-tool.svg`, our own, not Adobe's) is rendered to PNG / ICO
at build time with the bundled Qt (`packaging/icons.py`). Both builds use
python-build-standalone 3.13 fetched by uv (pinned, checksum-verified), and install from the
hashed `packaging/requirements.txt` (pinned versions, at least two weeks old when chosen).
Actions in the workflow are pinned by commit.

### Linux

`packaging/build-linux.sh` → `dist/Substance_Version_Tool-<version>-x86_64.AppImage` (about 75 MB).
Built in Debian 12 (`node:22-bookworm`) so bundled system libraries stay old; the glibc
floor is PySide6's 2.34. The AppImage is made without appimagetool (only a moving
"continuous" release): `mksquashfs` of the AppDir appended to the static type2 runtime
(pinned release 20251108, checksum-verified; no libfuse2 needed on the host). CI
smoke-tests it with `APPIMAGE_EXTRACT_AND_RUN=1`, since containers have no FUSE. Runs
locally with `podman run … code.forgejo.org/oci/node:22-bookworm` plus the apt packages
listed in the workflow.

* PySide6 6.10+ Linux wheels are `manylinux_2_34`; under Debian's own Python 3.11 with only
  2.28 allowed, pip silently falls back to PySide6 6.9.
* A frozen app sets `LD_LIBRARY_PATH` (and `_PYI_*`) to its bundle for child processes
  (in `--onedir` too: `<AppDir>/usr/lib/substance-version-tool/_internal`). `child_env()` undoes
  that for `Painter --version`, `xdg-open` and the AppImage restart; without it Painter or the
  file manager would load the app's Qt.
* Painter prints `--version` to **stderr**.
* Widgets added to a layout that is not yet attached to a widget stay "owned by Python" in
  PySide6 while Qt also owns them, which crashes at exit (SIGBUS in `destroyQCoreApplication`).
  Attach each row layout before filling it.
* The build image has no GTK, so the gtk3 platform-theme plugin's dependencies are not
  bundled (the host's GTK is used when present). The xcb libraries are installed so they
  get bundled; Ubuntu does not ship `libxcb-cursor0` by default.
* The bundled Python finds the system CA certificates on Debian and Fedora (checked with
  `--check-update`).

### Windows

`packaging/build-windows.sh` (Git Bash; stages `bundle`, `selftest`, `package`, `checksums`,
or all) → `Substance_Version_Tool-<version>-windows-x64-setup.exe` (Inno Setup,
`packaging/windows/substance-version-tool.iss`) and `…-windows-x64-portable.zip`.
`--windowed` (no console), with an `.ico` and a version resource (product name / version are
what SignPath checks). The installer is per-user by default (no admin), shows the privacy
note (`privacy.txt`) before installing, offers the update check (written to the app's
QSettings registry key only if no choice exists yet, so updates don't undo a change made in
the app) and the "Convert with Substance Version Tool" context-menu entry (through
`SystemFileAssociations`, so Painter keeps the double-click). Uninstalling removes the
settings. Never change the installer's `AppId`.

Still to check or do on Windows:

* non-ASCII file names, OneDrive and network folders, long paths
* a project that Painter has open (reading it; replacing an existing converted copy that
  Painter has open fails on Windows)
* `painter_executables()` knows only Linux locations, so on Windows the target is picked
  by hand. Detecting Painter there should read the `.exe` version resource or the uninstall
  registry entry rather than run it (it is a windowed program). Locations: Creative Cloud
  (`C:\Program Files\Adobe\Adobe Substance 3D Painter\`) and Steam.

### Code signing (SignPath Foundation)

Free for open-source projects; the certificate is issued to SignPath Foundation, which shows
as the publisher. Wired into the `windows` job and switched off until the repository has the
settings below; until then releases are unsigned and SmartScreen warns.

**SignPath application** (submitted 2026-11-16): project name "Substance Version Tool";
repository and homepage = the GitHub repo; download URL `…/releases/latest` (release notes
carry the code signing policy); privacy policy URL `…/blob/main/PRIVACY.md`; build system
GitHub Actions; maintainer type individual. Reputation was stated honestly as a young project
without wide adoption yet; that is the likeliest reason for a refusal.

**What SignPath's terms require, and where the repo has it:** "Free code signing provided by
SignPath.io, certificate by SignPath Foundation." under the term "Code signing policy" on the
home page (README) and download page (release notes); roles (Shadax: committer, reviewer,
approver); a privacy policy (`PRIVACY.md`, linking GitHub's for the update check) displayed
by the installer, with an installer option to turn the update check off; uninstall
instructions (README); file metadata restrictions (`packaging/signpath/*.xml` enforce product
name "Substance Version Tool" and product version = the `version` parameter the workflow
passes); MFA on GitHub and SignPath for every team member; builds only on GitHub-hosted
runners from the public source; manual approval of every release. Possible objection: Inno
Setup's own license is not OSI-approved (its stub is inside the installer); WiX or NSIS would
be the fallback.

**Turning signing on** after approval:

1. In SignPath: note the organization ID; check the project slug (expected
   `substance-version-tool`) and signing policy slug (`release-signing`); create the artifact
   configurations `app` and `installer` from `packaging/signpath/*.xml` (syntax follows
   docs.signpath.io, not yet validated by a live account); connect the GitHub repository as
   trusted build system; create an API token for a submitter.
2. GitHub repo → Settings → Secrets and variables → Actions: secret `SIGNPATH_API_TOKEN`,
   variable `SIGNPATH_ORGANIZATION_ID` (plus `SIGNPATH_PROJECT_SLUG` / `SIGNPATH_POLICY_SLUG`
   if they differ). Nothing goes into the code.
3. Tag a release and approve two signing requests in SignPath (the app; then the installer
   built from the signed app). The job waits up to 2 h for each; a check step fails the build
   if a signature is not valid; the release notes drop the "not signed yet" paragraph.
4. Remove the "application is pending" note from README's *Code signing policy*.
5. From then on, signed apps only install updates signed by the same publisher
   (`updater.check_publisher()`).

### Updates

`updater.py` (standard library only), used by the Help menu and a banner in the window.
Nothing is sent before the user agrees: the Windows installer's option, or the question on
first start (portable / AppImage / source); the answer is in QSettings `check_updates`
(`yes` / `no`). The check is a HEAD request to `github.com/<repo>/releases/latest` (the
redirect names the newest tag; no REST API, whose 60 requests per hour per IP a classroom
would exhaust). Install kinds: `installer` (Windows, `unins000.exe` next to the exe)
downloads the setup, checks its `.sha256` and runs it with
`/SILENT /SUPPRESSMSGBOXES /NORESTART /RELAUNCH` plus `/CURRENTUSER` or `/ALLUSERS` to match
the install (the `.iss` restarts the app on `/RELAUNCH`); `appimage` downloads next to
`$APPIMAGE`, checks it and renames it over the old file, then starts it; `portable` and
`source` open the release page. Old installer downloads in `%TEMP%\svt-update-*` are removed
on the next update. When the running Windows app is signed, a new installer must carry a
valid signature with the same signer subject. Tested on Linux against real releases
(download, checksum, refusal of a wrong checksum, banner flow, AppImage hand-over).

### 9.x / 10.x encoding

Releases up to 10.x write the Data serializer in an older **"inline" encoding**: header
word 0 instead of 1, and every object carries its class name and each field's name and
type, instead of a class table up front. The layout is in `sppformat._InlineReader`; it
was worked out from a real 9.1.2 project, which it reads and writes back byte for byte
(all nine blobs, also via the registry encoding and back). Enums take 8 bytes there.

Everything a 9.x / 10.x target reads is rewritten in it: documents, and every settings
blob, including the ones whose layout did not change (camera, colour profile, layer-stack
state). Three settings blobs get their pre-11.0 names back (`viewersettings.ini`,
`iraysettings.ini`, `layersstackstate.bin`). A settings blob that cannot be converted is
left out rather than left as saved, since those releases could not decode it. The final
check refuses a 9.x / 10.x output with any registry-encoded blob under `editor/`,
`baking/` or `paint/`.

10.1 is written inline too. The only 10.1 project at hand (`future_binary_data.spp`) has
header word 0xffffffff with a class table, a marker no normal save has, so 10.1's own
default is unknown, but 10.1 reads 10.0 projects, which are inline.

[Universal SPP](https://github.com/Yeusepe/Universal-Painter-Files) (MIT; it diffs real
8.1 / 9.0 / 10.0 / 11.0 / 12.0 / 12.1 projects) supplied the 9.0 and 10.0 rows of the table
above and the field lists used to check those targets. Its profiles also show 8.1 = data
version 70, below this tool's floor of 73.

What probing 12.0.1 could not show, and where it came from (`OLD_NAMES` / `REMOVED` in
`dev/gen_schemas.py`, emitted as `DOC_OLD_NAMES` / `DOC_REMOVED`):

* `DataBrushStamp` was called `DataBrush` before data version 82 (the 9.1.2 project;
  Universal SPP's 10.0 / 11.0 lists).
* The stroke layers had `projDuplicates` and `stencilPostBlending` (bools, usually 0)
  until data version 81 (paint layers in the 9.1.2 project; paint and eraser in Universal
  SPP's 9.0 list, not in its 10.0 list). Projection-paint, smudge and clone layers are
  given them by family, with no project to confirm (`DOC_REMOVED_ASSUMED`).
* `DataLayerInstance` (layer instancing) is known at version 80 only (`DOC_OLDER_SEEN`).
* `DataStroke3D` (3D paths) has no known layout before 88, so 9.x / 10.x outputs keep it as
  it is, with a warning. Universal SPP's 11.0 list already differs from 12.0's.

With those, the derived layouts equal the real 9.1.2 project's (37 classes, no mismatch).

## How the layouts were obtained

Painter's loader is **strict**. After its own upgrade steps, every class must have exactly
the fields the runtime expects. Found by experiment in 12.0.1:

* an unknown extra field → `[TRANSLATION] Members count mismatch in the source struct dict`
  or `A value has been defined for a NON-EXISTING member`
* a missing field → `[TRANSLATION] No value defined for '….field' member`
* the only field that may be absent is `uid`

So "drop what the old version does not know" requires knowing exactly what each version
knows. Painter 12.0.1 contains the upgrade chain from every older version, which makes it
an oracle: **a document stamped N with field F removed loads if and only if an upgrade
step after N adds F**. `dev/probe_fields.py` runs that test for every field (group
testing, about 900 project opens, 40 minutes) through `dev/oracle.py`, which drives a real
Painter with the plugin in `dev/oracle_plugin/`. The result is `dev/added_fields_12.0.1.json`,
and `dev/gen_schemas.py` turns it plus real projects into `schemas.py`.

Result (one feature per version):

| data version | fields added |
|---|---|
| 75 | `DataDocument.usePhysicalSizeAsDefault` |
| 76 | `Data2DTransformation.physicalSizeBoundedByScaleFactors` |
| 77 | `strokes3D` on paint / paint-proj / eraser / smudge / clone |
| 78 | `DataStroke.label` |
| 79 | `DataActionFill.uvTransferChannel` |
| 80 | `explicitPersistentCachePin` on layers and groups |
| 81 | `changeFlags` on the stroke actions; `DataSourceText.letterSpacing`, `lineSpacing` |
| 82 | `DataResolutionOverride` and the `resolutionOverride` fields using it |
| 83 | `DataActionFill.symmetry` (`DataSymmetry`) |
| 84 | `DataMaterialStack.type`, `typeMetadata` |
| 85 | `DataActionFill.changeFlags` |
| 89 | `DataGridDeformation.stickyBackupVertices`, `stickyState` |

Checks on this: the layouts derived for 80, 81, 82 and 88 equal the layouts in the real
9.1, 10.1, 11.0 and 11.1 projects (37, 12, 28 and 46 classes, no mismatch), with the
removals and the rename listed under "9.x / 10.x encoding".

Limits of the method, i.e. where an old Painter could still refuse a converted file:

* It finds fields that were **added**. A field that was renamed, removed or retyped
  between 73 and 89 does not show up: Painter 12.0.1 loads an old document that lacks it.
  Two such changes turned up in real 9.x projects (see "9.x / 10.x encoding"); there may
  be more in classes those projects do not contain.
* Below 73 something else changes (`Unknown struct type ''` at 70 – 72, a crash at ≤ 69,
  `Struct with non primitive member 'workflowLegacy'` at 60). 73 is the floor.
* Classes are assumed to exist in every version. A project using a layer or effect type
  newer than the target cannot be converted; the tool does not detect that.
* Classes with no 12.0 sample (`DataSourceVectorial`, `DataEmitterPhysics`: layouts from
  the 11.0 test projects; `DataActionClone`: copy of smudge) could not be probed.

## Format notes (reverse-engineered)

* An `.spp` file is HDF5 (Painter 12.0.1 links HDF5 1.14.4 statically, so output is
  written with `libver=('earliest','v114')`). Every dataset is a 1-D uint8 blob. Blobs
  under 64 KiB are contiguous; larger ones are chunked at 65536 with `maxshape=(None,)`.
* Dataset attribute `m3_x64_128` = MurmurHash3_x64_128(blob, **seed 0xF13A0239**),
  stored as two `>u8` (low, high).
* `paint/document.bin`, `paint/default_material.bin` and the settings blobs under
  `editor/` and `baking/` use Painter's "Data" serializer, which is little-endian and
  self-describing:
  `magic dd2f7c1b | u32 1 | u32 dataVersion | u32 18 | u32 classCount | root object`.
  An object is `u32 absoluteEndOffset (0 = null) | classref | fields`. A classref is
  `0xffffffff` followed by an inline definition (name and (field, typeId) list), or an
  index of an earlier definition. Type ids are listed in `sppformat.py`. Each blob kind
  has its own version counter (table above).
* Painter rejects a project when the document `dataVersion` is newer than its own (log
  message: "created with a newer version of Painter"). A too-new settings blob is only
  logged ("Data version (26) is more recent than the runtime version (23)") and replaced
  by defaults.
* **A settings blob with the right version but wrong content can crash Painter**: a
  post-effects blob "downgraded" 9 → 7 by filling the old, no longer existing sub-objects
  with nulls crashed 12.0.1 on open. The converter therefore refuses to convert a settings
  blob as soon as it would have to invent an object, and leaves it as saved.
* Changes between 89 and 92 that the converter handles:
  * `channelTypes`: type 22 (u128 mask) becomes type 12 (u64); take the low 8 bytes
  * `DataChannel.type` and `DataProceduralInput.channelType`: enum index (type 9,
    -1 = none) becomes a one-hot u64 (type 21, 0 = none). The channel numbering is
    unchanged. Same for `SettingsSolo.channelType` in the viewer settings (type 12).
  * `DataChannel.userIsColor` maps to `userIsColorManaged`
  * `sourceTransparent` on paint, eraser, smudge and clone: a single object (18)
    becomes a list (19)
  * polygon fill (`DataActionDecal` with hits): 12.2 keeps a source list plus blend and
    opacity on the action, and P and V on each hit. 12.0 keeps a `color` and
    `projViewInvMatrix = inverse(P·V)` on each hit (column-major). UV-view hits
    (`viewType 0`) have all-zero matrices in both versions.
  * 12.2-only fields are dropped; only values that differ from 12.2's defaults are
    reported (`KNOWN_DEFAULTS`, `schemas.DOC_USUAL`)
* `projectsettings.ini` is a big-endian QDataStream QVariantMap (values can be lists and
  maps, e.g. `baking/collapsed_materials`). The converter sets `versionAtLastSave/*` (and
  `versionAtCreation/*` if newer) to the target. The embedded auto-UV `anorigami` JSON is
  version 8 in 12.2, 7 in 12.0, 6 in 11.0 and `{}` in the 10.1 sample; key sets are in
  `ANORIGAMI_KEYS`.
* `texture-cache` holds the final per-channel composites:
  * header: QVariantMap {version 3, version.minor 2 → 3 in 12.2}, followed by
    (path, 8-byte tag) entries. 10.1, 11.0 and 12.0 all use 3.2.
  * channel dataset names: `1<<n` up to 12.0, `n` in 12.2
  * `list` entries: 12 bytes followed by a u64 BE mask (≤ 12.0) or a u32 BE index (12.2)
  * for 9.x / 10.0 targets the cache is dropped (its format there is unknown)
* 10.1 names three datasets without the "2": `editor/viewersettings.ini`,
  `iraysettings.ini`, `layersstackstate.bin`. The converter does not write those; 10.1 and
  older start with default viewer settings.
* Layouts for `DataActionSmudge`, `DataSourceText` and `DataTimelineKey` first came from
  older bundled presets; the converted student projects (which use them) load in 12.0.1.
* The smart materials / masks shipped with Painter (`.spsm`, `.spmsk`) carry three copies
  of their content, `preset.bin`, `preset_1.bin` (version 53) and `preset_2.bin` (54), in a
  numbering of their own. Not used by this tool.

## Desktop fixes (added 2026-11-15)

The launcher also sets `QT_SCALE_FACTOR`, preloads the eyedropper shim and adds
`painter/` to `SUBSTANCE_PAINTER_PLUGINS_PATH`. Facts found while building them:

* Painter ships only the xcb Qt platform plugin, so it always runs under XWayland. With
  xwayland-satellite the X screen is the output's physical size at 96 dpi.
* Python plugins in a `plugins/` folder are off until enabled in Painter's Python menu;
  modules in a `startup/` folder always load. That is why the plugin lives in `startup/`.
* `Camera.rotation` is XYZ Euler angles in degrees with `R = Rx * Ry * Rz`; the camera
  looks down local -Z. Measured by setting rotations, saving, and reading the quaternion
  in the project's `editor/camera.ini` (same Data serializer as `document.bin`).
* A Python-implemented `QObject` parented to Painter's main window crashes Painter on exit
  (it is destroyed after Python shuts down). Keep such objects unparented and delete them
  in `close_plugin`.
* Moving the camera through the API marks the project as modified.
* Tested by running Painter with a one-shot startup module that drives the plugin with
  synthetic key events and checks the camera, and that calls `QScreen.grabWindow(0)`.
  **Not tested with physical key presses or with the eyedropper tool itself.**

## Other open items

1. **Linux launcher: detect the installed Painter.** `install.sh` bakes `PAINTER_VERSION`
   (default 12.0.1) into the launcher. It could parse `--version` (see the top section)
   and pass the result as `--to` instead.
2. **9.x / 10.x leftovers:** resources (export presets, `resources/*.spexp`) stay in the
   registry encoding at their newer data version, with a warning; 3D path layers
   (`DataStroke3D`) are kept in today's layout, with a warning; the `workflow/UVTiles`
   project setting that 9.1 has is not written (10.1 does not have it either). A 9.0 or
   10.0 project, or one with smudge / clone / projection-paint layers saved by 9.x, would
   settle the remaining assumptions (`DOC_REMOVED_ASSUMED`).
3. Open a converted project in a real 12.1 / 11.x / 10.x / 9.x if one is ever at hand. So
   far: 9.0 / 9.1 / 10.0 / 10.1 outputs of 12.0, 12.1 and 12.2 projects all open in Painter
   12.0.1 (which also reads the inline encoding). The real 9.1.2 project itself crashed
   12.0.1 on open; not investigated.
4. Effect display names in Painter 12.0.1 sometimes show the resource id ('card_diamonds',
   'blur') instead of the name ('Card Diamonds', 'Blur') for a converted project. It is
   Painter's doing, not the file's: opened again in the same session, the same 9.0 / 10.0
   files show the right names, and a 10.1 file that was right before shows the ids.
   Everything else in the layer tree matched the 12.0 original for 9.0 / 9.1 / 10.0 / 10.1.
5. A project newer than data version 92 is refused unless `--force` is given. To support a
   newer Painter: add its changes as rules in `DataConverter` (compare its layouts with
   `schemas.DOC_89`), and if the installed Painter is newer too, re-run the probe so
   `DOC_ADDED` covers the new base. To make 12.2 a target then, run `dev/gen_schemas.py`
   with 12.2 projects once `NEWEST_DATA_VERSION` is raised: it builds `DOC_NEWER[92]`.
6. Settings blobs with no conversion: post-effects 9 → 8 / 7 (targets 11.1 and older) fails
   because `DataPostEffectsParameters` points at older-style objects the newer blob does not
   have, so those releases use their default post effects (for 10.x and older the blob is
   left out). In settings lists, entries of classes the target lacks are left out
   (`DataConverter._keep`), and a 12.2 bake template becomes null. `DataReferenceBinding` (seen in 12.1 projects)
   has no known layout before 12.1 and is kept as it is, with a warning.
7. `DataStroke3D` gained `stickyBackupPoints` / `stickyState` somewhere in 89 – 91, so its
   12.0 layout is unknown (`DOC_OLDER_SEEN` holds its 11.1 layout). The 12.0.1 probe could
   settle it.

  disagrees with a recorded layout, so it only needs the projects that bring something new
  (12.1 and 11.1 were added from `~/Documents/Development/spp-samples/`). A rerun with the
  same inputs leaves `schemas.py` unchanged.
